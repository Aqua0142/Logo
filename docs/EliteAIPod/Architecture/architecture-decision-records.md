## ADR-001 — Use Argon2id for Password Hashing

**Status:** accepted

**Context:** The critical NFR requires all user passwords to be salted and hashed using a strong modern algorithm. The project handles PHI and must comply with HIPAA security best practices. bcrypt is widely used but has known weaknesses against GPU attacks at low cost factors. Argon2id is the winner of the Password Hashing Competition (2015) and is recommended by OWASP and NIST as of 2024.

**Decision:** Use Argon2id via passlib[argon2] with parameters: memory_cost=65536 (64MB), time_cost=3, parallelism=4. These parameters are validated against OWASP's recommended minimums and adjusted to keep login latency under 500ms on prototype hardware.

**Alternatives considered:**
- bcrypt: Widely supported but memory-hard parameters are limited; rejected in favor of stronger Argon2id
- scrypt: Memory-hard but less widely validated than Argon2id for PHI workloads
- PBKDF2: FIPS-compliant but weaker against GPU attacks; rejected
**Consequences:**
- Login endpoint latency increases by ~100-300ms due to memory-hard hashing — acceptable given the 500ms API NFR applies to blood work results, not login
- Password verification is resistant to GPU-based brute force attacks
- passlib dependency must be kept updated as Argon2 parameter recommendations evolve
_Related: US-001, NFR-security-password-hashing_
## ADR-002 — Use NUMERIC Type and SQLAlchemy TypeDecorator for Blood Work Value Precision

**Status:** accepted

**Context:** The data integrity NFR requires that blood work numeric values (e.g., hemoglobin 14.2 g/dL, glucose 98.5 mg/dL) are stored and retrieved with exact decimal precision. PostgreSQL FLOAT and Python float types use IEEE 754 binary floating point which can introduce rounding errors (e.g., 14.2 stored as 14.199999999). Incorrect lab values could mislead patients about their health status.

**Decision:** Use PostgreSQL NUMERIC(10,4) for all blood work value columns. Return values as strings in API responses to preserve precision across JSON serialization. Use SQLAlchemy TypeDecorator to handle transparent AES-256 encryption of the value column while maintaining NUMERIC semantics for comparison queries.

**Alternatives considered:**
- FLOAT / DOUBLE PRECISION: Fast but introduces binary rounding errors for decimal values; rejected due to data integrity NFR
- Store as VARCHAR: Avoids rounding but loses ability to perform range comparisons in SQL; rejected
- DECIMAL (alias for NUMERIC): Equivalent to NUMERIC in PostgreSQL; no material difference
**Consequences:**
- NUMERIC arithmetic is slightly slower than FLOAT for is_out_of_range comparisons — negligible at prototype scale
- API clients receive value as string and must parse it; documented in API contract
- AES-256 encryption of NUMERIC column requires storing encrypted bytes and comparing against decrypted values in application layer, not in SQL WHERE clause — acceptable for prototype scale
_Related: US-006, US-007, NFR-security-phi-encryption_
## ADR-003 — Use Modular Monolith Pattern with Internal Module Boundaries

**Status:** accepted

**Context:** The project is a small-scale internal prototype with fewer than 50 concurrent users. Microservices would add significant operational overhead (service discovery, inter-service auth, distributed tracing, separate deployments) without providing scalability benefits at this scale. However, a flat monolith with no module boundaries would make future decomposition harder and violate separation of concerns for auth vs blood work logic.

**Decision:** Adopt a modular monolith architecture with two internal FastAPI modules: auth (login, logout, RBAC) and blood_work (record creation, results retrieval). Each module has its own router, service, and repository layer. Modules communicate only through well-defined interfaces (shared models and the JWT Depends injection). The internal structure mirrors what would become microservice boundaries if the system scales.

**Alternatives considered:**
- Microservices: Provides independent scalability and deployment but excessive operational overhead for a prototype; rejected
- Flat monolith: Simple but no clear boundaries, makes testing and future decomposition harder; rejected
- Serverless functions: Low ops burden but cold starts risk violating <500ms NFR; rejected
**Consequences:**
- Single deployable unit simplifies CI/CD and Docker Compose setup for the prototype
- Clear module boundaries allow future decomposition into microservices without a full rewrite
- All business logic runs in the same process — no network latency between auth and blood work modules
- A bug in one module can affect the other — mitigated by typed interfaces and comprehensive tests
_Related: US-001, US-002, US-005, US-006, US-007, NFR-performance_
## ADR-004 — Server-Side Session Invalidation for JWT Logout

**Status:** accepted

**Context:** Pure stateless JWTs cannot be invalidated before expiry. The logout NFR requires that session termination is enforced server-side and that back-navigation to authenticated pages is prevented. An 8-hour JWT expiry means a stolen or logged-out token remains valid for hours if only client-side deletion is used.

**Decision:** Implement a sessions table that stores a jti (JWT ID) claim for each active session. On logout, the jti is deleted from the sessions table. Every protected request verifies the JWT signature AND checks that the jti exists in the sessions table. A missing jti returns 401, effectively invalidating the token server-side.

**Alternatives considered:**
- Redis token denylist: Faster lookups but adds a Redis dependency; rejected to keep prototype dependencies minimal
- Short-lived JWTs (5 minutes) with refresh tokens: Reduces exposure window but adds complexity; rejected for prototype simplicity
- Client-side only deletion: Insufficient — does not prevent token reuse after logout; rejected due to security NFR
**Consequences:**
- Every authenticated request incurs one additional DB query for session validation — acceptable at prototype scale (<50 users)
- Sessions table must be cleaned up for expired tokens — a periodic background task or on-login cleanup is needed
- Provides true server-side logout security, satisfying the logout acceptance criteria
_Related: US-002, NFR-security-rbac_
## ADR-005 — AES-256 Encryption for PHI Fields via SQLAlchemy TypeDecorator

**Status:** accepted

**Context:** The critical security NFR requires all PHI to be encrypted at rest using AES-256. The blood_work_results table contains two PHI fields: patient_id (a UUID linking a medical record to an identity) and value (a medical measurement). PostgreSQL's pgcrypto extension can encrypt individual columns, but integrating encryption transparently at the ORM layer reduces the risk of a developer accidentally persisting unencrypted PHI.

**Decision:** Implement a SQLAlchemy TypeDecorator (EncryptedType) that transparently AES-256-CBC encrypts PHI column values before INSERT and decrypts after SELECT. The encryption key is loaded from an environment variable (never hardcoded). Applied to patient_id and value columns in blood_work_results.

**Alternatives considered:**
- Full-disk encryption only: Protects against physical theft but not against SQL injection or compromised DB accounts; rejected
- PostgreSQL pgcrypto directly: Encryption logic lives in SQL; harder to audit and test at the application layer; considered but ORM approach preferred
- Application-level encryption without TypeDecorator: Requires every query site to manually call encrypt/decrypt; error-prone; rejected
**Consequences:**
- Encrypted PHI columns cannot be used in SQL WHERE clauses or indexes — application must decrypt and filter in-memory for small datasets (acceptable for prototype scale)
- AES-256-CBC requires IV storage alongside ciphertext — stored as base64-encoded prefix in the column
- Encryption key rotation requires re-encrypting all existing rows — documented as a maintenance procedure
_Related: US-006, US-007, NFR-security-phi-encryption_
