## Risks

- **[MEDIUM]** Product image assets and mock data quality: the catalog and detail pages depend on realistic product data (images, descriptions, ingredients). If placeholder images are low quality or data is sparse, the UI review gate may require rework cycles that delay Sprint 1 sign-off.
  - _Mitigation:_ Seed the mock data layer (T-002) with at least 8 well-structured products using freely available placeholder images (e.g., Unsplash, Picsum) and realistic OTC product descriptions. Review mock data at the T-002 gate before building dependent components.
- **[HIGH]** WCAG 2.1 AA compliance across all components: accessibility requirements are marked critical. Colour contrast, keyboard navigation, and ARIA labelling must be correct from the start. Retrofitting accessibility after components are built is costly.
  - _Mitigation:_ Enforce accessibility as a definition-of-done criterion for every frontend task. Use automated tooling (e.g., axe-core or Lighthouse) during development. Include accessibility acceptance criteria in the human review gate for T-001, T-003, T-005, and T-006.
- **[MEDIUM]** localStorage cart persistence and security: the PRD requires that no sensitive user data be stored in localStorage without appropriate security measures. Cart data (product IDs, quantities, prices) is not personally identifiable, but the implementation must be reviewed to confirm no PII leaks into storage.
  - _Mitigation:_ Restrict localStorage cart schema to product ID, quantity, and cached display price only. Conduct a targeted security review of T-004 at the gate to confirm no PII or session tokens are persisted. Document the storage schema in the task output.
- **[HIGH]** LCP performance target (<3 seconds) for catalog and detail pages: product images are the dominant LCP element. Without lazy loading and appropriate image sizing, the performance NFR may be missed.
  - _Mitigation:_ Implement lazy loading for off-screen product images in T-001. Use appropriately sized images in the mock data layer (T-002). Run a Lighthouse performance audit as part of the Sprint 1 review gate and flag any LCP regression before Sprint 2 begins.
- **[MEDIUM]** Single-sprint frontend dependency chain: all Sprint 2 tasks depend on Sprint 1 deliverables (T-003, T-002). Any slip in Sprint 1 completion directly delays the entire cart feature set with no parallel work available.
  - _Mitigation:_ Prioritise T-002 (mock data service) as the first task in Sprint 1 since it unblocks both T-001 and T-003. Ensure Sprint 1 tasks are reviewed and approved before Sprint 2 begins. The 2-sprint structure provides a natural gate between discovery and cart work.
