## Project Summary

This project aims to build a full-stack application for viewing patient blood work results. The system will feature a clean, dark-mode user interface for three distinct user roles: Patients, Lab Technicians, and Hospital Administrators. Key functionality includes manual data entry, JSON file uploads of lab results, and automatic conditional formatting to highlight any values that fall outside of standard medical reference ranges. The initial scope is for a small-scale internal prototype.

## Business Context

The business domain research was instrumental in shaping the non-functional requirements and acceptance criteria. Security NFRs are heavily influenced by HIPAA best practices, mandating encryption (in transit and at rest) and role-based access control (RBAC), which is critical given the multiple user roles identified. UX best practices for dark mode (e.g., using dark gray instead of pure black, ensuring WCAG AA contrast ratios) and data table design have been incorporated into the ACs for the UI stories. Performance benchmarks, such as sub-500ms API response times, were adopted from industry standards for patient-facing applications. The research on common user workflows confirmed the importance of clear navigation and handling of empty/error states, which are addressed in the Core User Experience epic. While the research highlighted advanced features like FHIR integration, trend visualization, and AI summaries, these were deliberately excluded to adhere strictly to the user's core requirements, following the 'Silence is not permission' principle.

## Epics

### 1. Authentication & User Management

Handles user login, logout, and session management for all roles.

**Stories in this epic:** US-001, US-002

### 2. Data Input & Management

Covers the creation of blood work records by authorized personnel.

**Stories in this epic:** US-005, US-006

### 3. Blood Work Visualization

Focuses on how different user roles view and interpret blood work data.

**Stories in this epic:** US-007

### 4. Core User Experience

Ensures the application is navigable, accessible, and provides a consistent experience.

**Stories in this epic:** US-011


## User Stories

### US-001 — User Login

**As a** Patient, Lab Technician, or Administrator
**I want** to securely log into the application with my credentials
**So that** I can access the features relevant to my role.

- **Epic:** Authentication & User Management
- **Priority:** critical
- **Story Points:** 3

**Acceptance Criteria:**
- Given I am on the login page, When I enter valid credentials for my role, Then I am redirected to my role-specific dashboard.
- Given I am on the login page, When I enter invalid credentials, Then I see an error message and remain on the login page.
- Given my role, When I log in, Then I only have access to functionality permitted for that role.

### US-002 — User Logout

**As a** logged-in user
**I want** to log out of the application
**So that** my session is securely terminated.

- **Epic:** Authentication & User Management
- **Priority:** high
- **Story Points:** 1
- **Depends on:** US-001
**Acceptance Criteria:**
- Given I am logged in, When I click the 'Logout' button, Then my session is terminated and I am redirected to the login page.
- Given I have logged out, When I use the browser's back button, Then I cannot access the previous authenticated page.

### US-005 — Manually Enter Blood Work Results

**As a** Lab Technician
**I want** to use a form to manually enter a patient's blood work results
**So that** I can input data that is not available in a JSON file.

- **Epic:** Data Input & Management
- **Priority:** high
- **Story Points:** 3
- **Depends on:** US-001
**Acceptance Criteria:**
- Given I am on the data entry page, When I fill out the required fields (e.g., Patient ID, Test Name, Value, Units) and submit the form, Then the record is saved and I see a confirmation message.
- Given I attempt to submit the form with missing or invalid data, Then I see validation errors next to the corresponding fields.

### US-006 — Parse and Store Blood Work Data

**As a** system
**I want** to parse and store blood work data from JSON uploads or manual entry
**So that** it can be retrieved and displayed to users.

- **Epic:** Data Input & Management
- **Priority:** critical
- **Story Points:** 5
- **Depends on:** US-005
**Acceptance Criteria:**
- Given new blood work data is submitted, When the system processes it, Then the data is correctly stored in the database, associated with the correct patient.
- Given a value is stored, When it is retrieved, Then the data integrity (e.g., numeric precision) is maintained.

### US-007 — View My Recent Blood Work

**As a** Patient
**I want** to view a list of my recent blood work results
**So that** I can stay informed about my health.

- **Epic:** Blood Work Visualization
- **Priority:** critical
- **Story Points:** 3
- **Depends on:** US-001, US-006
**Acceptance Criteria:**
- Given I am logged in and have results, When I navigate to the results page, Then I see a table with columns for Test Name, My Value, Standard Range, and Units.
- Given I have no blood work results in the system, When I navigate to the results page, Then I see a message indicating 'No results found'.
- Given there is an error fetching my data, When I navigate to the results page, Then I see a user-friendly error message.

### US-011 — Application Navigation

**As a** user
**I want** to easily navigate between the main sections of the application
**So that** I can find the information I need without having to know the direct URLs.

- **Epic:** Core User Experience
- **Priority:** high
- **Story Points:** 2
- **Depends on:** US-001
**Acceptance Criteria:**
- Given I am logged in, When I view the application, Then a persistent navigation bar or menu is visible.
- Given I am a Lab Technician, When I view the navigation menu, Then I see links for 'Data Entry' and 'View Results'.
- Given I am a Patient, When I view the navigation menu, Then I see a link for 'My Results'.


## Non-Functional Requirements

- **security** (critical): All user passwords must be salted and hashed using a strong, modern algorithm (e.g., Argon2, bcrypt).- **security** (critical): The system must implement Role-Based Access Control (RBAC) to ensure users can only access data and functions appropriate for their role (e.g., a Patient cannot see another patient's data).- **security** (critical): All Protected Health Information (PHI) must be encrypted at rest in the database (e.g., AES-256) and in transit (using TLS 1.3).- **performance** (high): API response times for fetching patient results must be under 500ms for a typical user load.- **performance** (medium): The web interface should achieve a First Contentful Paint (FCP) of under 1.8 seconds.- **usability** (high): The user interface must be intuitive and require minimal training for all user roles.- **accessibility** (medium): The frontend application must meet Web Content Accessibility Guidelines (WCAG) 2.1 Level AA standards.- **reliability** (high): The application must handle errors gracefully, presenting user-friendly error messages instead of crashing or showing technical stack traces.
## Assumptions

- The application is an internal prototype and does not require integration with external EHR/EMR systems via APIs like FHIR at this stage.
- A predefined, hard-coded list of standard medical reference ranges for blood work is sufficient for the initial version.
- User accounts and roles (Patient, Lab Technician, Administrator) will be pre-provisioned; self-registration is not in scope.
- The application will be deployed in a single language (English).
- The volume of data will be small (hundreds of records), and the number of concurrent users will be low (<50), as per the clarification.
